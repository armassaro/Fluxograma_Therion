## 1. OBJETIVO E ESCOPO

Automatizar a comunicação e o acompanhamento de projetos entre as diretorias **Comercial, Projetos,
Financeiro e Administrativo** de uma Empresa Júnior. Cada projeto percorre um fluxo de etapas; membros
executam **ações** por um canal de mensagens (Telegram, WhatsApp, E-mail) ou formulário (Google Forms);
o sistema valida permissão, registra o evento, move o projeto, organiza arquivos no Drive, gera
documentos com IA (com validação humana) e notifica os responsáveis da próxima etapa.

Tipos de serviço iniciais (catálogo extensível sem alterar código):
- `impressao_modelagem_3d` — Impressão e/ou Modelagem 3D
- `website` — Websites

Fora de escopo (v1): portal web completo para clientes; emissão fiscal; integração bancária automática.

## 2. GLOSSÁRIO

| Termo | Significado |
|---|---|
| Projeto | Instância de um serviço para um cliente. É o **grafo**. |
| Etapa | Estado do projeto no fluxo (nó do grafo). Tem diretoria responsável. |
| Ação | Evento que move (ou não) o projeto entre etapas (aresta do grafo). Imutável. |
| Template de fluxo | Definição declarativa de etapas, transições e campos exigidos por tipo de serviço. |
| Evento | Registro imutável na tabela `acoes` (event sourcing). Estado atual é derivado/projetado. |
| Diretoria | comercial, projetos, financeiro, administrativo (+ papel especial `presidencia`/`admin`). |
| Canal | telegram, whatsapp, email, forms. |
| Responsável atribuído | Pessoa (não só diretoria) designada por rodízio para uma etapa. |
| Lead | Contato/cliente potencial que originou o projeto. |

## 3. DECISÕES DE ARQUITETURA (com justificativa)

1. **Orquestração: n8n self-hosted** (Docker). Backend próprio é alternativa menos provável; a lógica
   de domínio fica isolada em Code nodes/arquivos JS reutilizáveis para permitir migração futura.
2. **Persistência: PostgreSQL** (mesmo container stack do n8n). Substitui o "arquivo de log por
   projeto", que é frágil a concorrência e impede consultas agregadas.
3. **Event sourcing leve**: toda ação é um INSERT em `acoes` (nunca UPDATE/DELETE). A tabela `projetos`
   é uma projeção (cache do estado atual) atualizada na mesma transação. Retroceder = nova ação do
   tipo `reverter`. Isso entrega auditoria e "desfazer" gratuitamente.
   - O "arquivo de logs por projeto" do requisito original é mantido como **exportação**: um
     `log.jsonl` na pasta do projeto no Drive, regenerado a cada ação (legível por humanos/backup).
4. **Fluxo configurável**: templates YAML/JSON versionados em `fluxos/` e carregados para a tabela
   `templates_fluxo`. Novo serviço = novo arquivo, sem código.
5. **Exposição segura**: n8n escuta só na rede Tailscale; Cloudflare Tunnel expõe apenas os paths de
   webhook (`/webhook/*`) com WAF; UI do n8n só via Tailscale.
6. **Membros**: Google Sheets é a fonte de verdade editável pela EJ; sincronizado para a tabela
   `membros` a cada 15 min (e sob demanda). Validação por requisição consulta o Postgres (rápido).
7. **Fluxograma visual**: Mermaid → PNG via container `mermaid-cli` (ou Kroki) chamado por HTTP.
8. **IA**: provedor configurável via env (padrão: Anthropic Claude, modelo `claude-sonnet-5-5`).
   Documentos gerados SEMPRE como rascunho → validação humana obrigatória.

## 4. ARQUITETURA

```
                ┌───────────── Usuários (membros da EJ) ──────────────┐
                │ Telegram   WhatsApp(Cloud API)   E-mail   G. Forms  │
                └────┬──────────┬─────────────────┬────────┬──────────┘
                     │ webhook  │ webhook         │ IMAP   │ Apps Script → webhook
                     ▼          ▼                 ▼        ▼
          Cloudflare Tunnel (WAF, só /webhook/*) ──► Tailscale ──► host
                     │
              ┌──────▼───────────────────────── n8n ─────────────────────────────┐
              │ WF-01 Entrada/Normalização ─► WF-02 Identificação/Autorização     │
              │        ─► WF-03 Roteador de Comandos ─► WF-04 Motor de Fluxo      │
              │ WF-05 Notificações   WF-06 Drive/Docs   WF-07 IA Documentos       │
              │ WF-08 Fluxograma     WF-09 Sync Membros WF-10 SLA/Lembretes       │
              │ WF-11 Backup/Export  WF-12 Relatório    WF-99 Error Handler       │
              └──────┬────────────────────────┬───────────────────┬──────────────┘
                     ▼                        ▼                   ▼
                PostgreSQL           Google Drive/Docs/Sheets   Mermaid renderer / LLM API
```

Fluxo de uma requisição (resumo):
`mensagem → normaliza (canal-agnóstico) → identifica membro → interpreta comando → valida
permissão + transição + campos → transação (INSERT acao, UPDATE projeto, etapa) → efeitos
(Drive, IA, export log) → notifica responsáveis → responde ao remetente`.

## 5. MODELO DE DADOS (PostgreSQL)

Hierarquia lógica: Projeto(Etapa(Ação())). Todas as datas em `timestamptz` (ISO 8601, UTC no banco,
exibidas em America/Sao_Paulo).

```sql
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- Diretorias e papéis
CREATE TYPE diretoria_t AS ENUM ('comercial','projetos','financeiro','administrativo','presidencia');
CREATE TYPE canal_t     AS ENUM ('telegram','whatsapp','email','forms');
CREATE TYPE status_projeto_t AS ENUM ('ativo','pausado','concluido','abandonado');

-- Membros (projeção da planilha)
CREATE TABLE membros (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  nome             text NOT NULL,
  email            text UNIQUE NOT NULL,
  telefone_e164    text UNIQUE,            -- +5511999999999 (WhatsApp)
  telegram_user_id bigint UNIQUE,          -- preenchido no vínculo
  diretoria        diretoria_t NOT NULL,
  is_admin         boolean NOT NULL DEFAULT false,  -- pode agir em qualquer etapa
  ativo            boolean NOT NULL DEFAULT true,   -- false = desligado (offboarding)
  disponivel       boolean NOT NULL DEFAULT true,   -- false = férias/ausente (sai do rodízio)
  cargo            text NOT NULL DEFAULT 'membro' CHECK (cargo IN ('membro','diretor')), -- coluna 'cargo' da planilha
  canal_preferido  canal_t NOT NULL DEFAULT 'email',
  canais_habilitados canal_t[] NOT NULL DEFAULT '{email}',
  sincronizado_em  timestamptz
);

-- Clientes
CREATE TABLE clientes (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  nome        text NOT NULL,
  documento   text,               -- CPF/CNPJ (dado pessoal: ver LGPD)
  email       text,
  telefone    text,
  criado_em   timestamptz NOT NULL DEFAULT now()
);

-- Templates de fluxo versionados (conteúdo = JSON do YAML de fluxos/)
CREATE TABLE templates_fluxo (
  tipo_servico text NOT NULL,
  versao       int  NOT NULL,
  definicao    jsonb NOT NULL,
  ativo        boolean NOT NULL DEFAULT true,
  PRIMARY KEY (tipo_servico, versao)
);

-- Projeto (projeção do estado atual)
CREATE TABLE projetos (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  codigo                text UNIQUE NOT NULL,   -- humano: "P-2026-0042" (usado nos chats)
  nome                  text NOT NULL,
  cliente_id            uuid NOT NULL REFERENCES clientes(id),
  nome_lead             text NOT NULL,
  tipo                  text NOT NULL,          -- tipo_servico
  template_versao       int  NOT NULL,          -- projeto fica preso à versão com que nasceu
  membro_original_id    uuid NOT NULL REFERENCES membros(id),
  etapa_atual_id        uuid,                   -- FK adicionada abaixo
  status                status_projeto_t NOT NULL DEFAULT 'ativo',
  estimativa_horas      numeric,
  estimativa_filamento_g numeric,
  valor_orcado          numeric(12,2),
  valor_contratado      numeric(12,2),
  link_pasta_drive      text,
  data_inicio           timestamptz NOT NULL DEFAULT now(),
  data_final            timestamptz,            -- set quando concluido/abandonado
  versao                int NOT NULL DEFAULT 0, -- controle de concorrência otimista
  FOREIGN KEY (tipo, template_versao) REFERENCES templates_fluxo(tipo_servico, versao)
);

-- Etapa (instância de uma etapa do template dentro de um projeto; uma linha por entrada)
CREATE TABLE etapas (
  id                     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  projeto_id             uuid NOT NULL REFERENCES projetos(id),
  chave                  text NOT NULL,          -- ex: 'orcamento' (do template)
  nome                   text NOT NULL,
  diretoria_responsavel  diretoria_t NOT NULL,
  responsavel_atribuido_id uuid REFERENCES membros(id),
  data_entrada           timestamptz NOT NULL DEFAULT now(),
  data_saida             timestamptz,
  prazo_sla              timestamptz            -- data_entrada + sla_horas
);
ALTER TABLE projetos ADD CONSTRAINT fk_etapa_atual FOREIGN KEY (etapa_atual_id) REFERENCES etapas(id);

-- Ação (EVENTO IMUTÁVEL; aresta do grafo)
CREATE TABLE acoes (
  id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  projeto_id        uuid NOT NULL REFERENCES projetos(id),
  seq               int  NOT NULL,              -- 1,2,3... por projeto
  tipo_acao         text NOT NULL,              -- ver §6 (ex: 'enviar_escopo','reverter','pausar')
  etapa_origem_id   uuid REFERENCES etapas(id),
  etapa_destino_id  uuid REFERENCES etapas(id), -- null se não muda de etapa
  status_anterior   status_projeto_t NOT NULL,
  status_novo       status_projeto_t NOT NULL,
  membro_id         uuid NOT NULL REFERENCES membros(id),
  nome_responsavel  text NOT NULL,              -- desnormalizado p/ auditoria
  canal_origem      canal_t NOT NULL,
  dados             jsonb NOT NULL DEFAULT '{}',-- campos exigidos pelo template
  observacoes       text,
  arquivos          jsonb NOT NULL DEFAULT '[]',-- [{drive_file_id, nome, url, mime}]
  revertida_por_id  uuid REFERENCES acoes(id),  -- único UPDATE permitido (marcação)
  reverte_acao_id   uuid REFERENCES acoes(id),  -- preenchido em ações 'reverter'
  idempotency_key   text UNIQUE NOT NULL,       -- ver §19
  criado_em         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (projeto_id, seq)
);

-- Documentos gerados por IA aguardando validação
CREATE TABLE documentos (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  projeto_id    uuid NOT NULL REFERENCES projetos(id),
  tipo          text NOT NULL CHECK (tipo IN ('orcamento','contrato')),
  versao        int  NOT NULL,
  status        text NOT NULL CHECK (status IN ('rascunho','aprovado','reprovado','enviado_cliente')),
  drive_doc_id  text NOT NULL,
  gerado_por    text NOT NULL,                 -- 'ia:<modelo>' ou membro
  validado_por_id uuid REFERENCES membros(id),
  motivo_reprovacao text,
  criado_em     timestamptz NOT NULL DEFAULT now()
);

-- Estado do rodízio por diretoria/etapa
CREATE TABLE rodizio (
  chave_etapa   text NOT NULL,
  diretoria     diretoria_t NOT NULL,
  ultimo_membro_id uuid REFERENCES membros(id),
  PRIMARY KEY (chave_etapa, diretoria)
);

-- Códigos de vínculo de canal
CREATE TABLE vinculos_pendentes (
  codigo      text PRIMARY KEY,                -- 6 dígitos
  membro_id   uuid NOT NULL REFERENCES membros(id),
  canal       canal_t NOT NULL,
  expira_em   timestamptz NOT NULL
);

-- Sessões de conversa (para menus/diálogos multi-passo nos bots)
CREATE TABLE sessoes_chat (
  canal       canal_t NOT NULL,
  id_externo  text NOT NULL,
  estado      jsonb NOT NULL,
  expira_em   timestamptz NOT NULL,
  PRIMARY KEY (canal, id_externo)
);

-- Notificações (outbox p/ reenvio)
CREATE TABLE notificacoes (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  membro_id   uuid REFERENCES membros(id),
  canal       canal_t NOT NULL,
  payload     jsonb NOT NULL,
  status      text NOT NULL DEFAULT 'pendente' CHECK (status IN ('pendente','enviada','falhou')),
  tentativas  int NOT NULL DEFAULT 0,
  erro        text,
  criado_em   timestamptz NOT NULL DEFAULT now(),
  enviada_em  timestamptz
);

-- Proteção: acoes são append-only
CREATE OR REPLACE FUNCTION bloquear_alteracao_acoes() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'DELETE' THEN RAISE EXCEPTION 'acoes é append-only'; END IF;
  -- UPDATE: só permite preencher revertida_por_id (uma vez); qualquer outra mudança é bloqueada
  IF OLD.revertida_por_id IS NOT NULL
     OR (to_jsonb(NEW) - 'revertida_por_id') IS DISTINCT FROM (to_jsonb(OLD) - 'revertida_por_id') THEN
    RAISE EXCEPTION 'apenas revertida_por_id pode ser preenchido, uma única vez';
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

-- Idempotência de requisições (inclusive consultas que não geram ação)
CREATE TABLE requisicoes_processadas (
  idempotency_key text PRIMARY KEY,
  resposta        jsonb NOT NULL,
  criado_em       timestamptz NOT NULL DEFAULT now()
);
CREATE TRIGGER trg_acoes_append_only BEFORE UPDATE OR DELETE ON acoes
  FOR EACH ROW EXECUTE FUNCTION bloquear_alteracao_acoes();

CREATE INDEX ON acoes (projeto_id, seq);
CREATE INDEX ON projetos (status, etapa_atual_id);
CREATE INDEX ON etapas (projeto_id, data_saida);
```

Observações sobre o modelo original corrigidas:
- `status` saiu da Ação e foi para o Projeto; a Ação registra `status_anterior → status_novo`.
- ID da Ação era descrito como "ID da etapa" (erro) → corrigido.
- Ação ganhou `criado_em`, `etapa_origem_id`, `etapa_destino_id` (definem a aresta).
- Etapa ganhou `data_saida`, `responsavel_atribuido_id`, `prazo_sla`.
- Projeto ganhou cliente, valores, estimativas, link da pasta, código legível e `versao`.

## 6. TEMPLATES DE FLUXO (máquina de estados configurável)

Arquivo por serviço em `fluxos/<tipo_servico>.yaml`. Carregado por script `scripts/carregar_fluxos.js`
(valida com JSON Schema `fluxos/schema.json` e insere nova versão em `templates_fluxo`).

Formato:
```yaml
tipo_servico: website
nome_exibicao: "Websites"
versao: 1
etapa_inicial: registro_lead
etapas:
  <chave>:
    nome: "Nome legível"
    diretoria: comercial|projetos|financeiro|administrativo
    sla_horas: 48                # para lembretes (§8.6)
    rodizio: true|false          # atribuir pessoa automaticamente (§8.5)
    terminal: false              # etapas finais
    status_projeto: concluido    # (só em terminais) status a aplicar
transicoes:
  - acao: <tipo_acao>
    de: <chave_etapa>
    para: <chave_etapa>
    rotulo: "Texto do botão"
    campos:                      # validados no motor
      - { nome: estimativa_horas, tipo: number, obrigatorio: true, min: 0 }
      - { nome: arquivo_escopo, tipo: arquivo, obrigatorio: false }
    efeitos: [gerar_orcamento_ia, criar_pasta_drive, ...]   # ver §18 "efeitos"
```

Ações globais (valem para qualquer etapa não-terminal, definidas no motor, não no YAML):
- `pausar` (status ativo→pausado; campo obrigatório `motivo`)
- `retomar` (pausado→ativo)
- `abandonar` (→abandonado; campo obrigatório `motivo`; define data_final; vai a etapa terminal `abandonado`)
- `reverter` (desfaz a última ação não revertida; §8.3)
- `comentar` (não muda etapa; só registra observação/arquivo)
- `reatribuir` (troca responsável atribuído da etapa atual; só admin ou diretor da diretoria)

```yaml
    para: execucao
    campos:
      - { nome: ajustes, tipo: text, obrigatorio: true }
  - acao: cliente_aceitou_entrega
    de: entrega
    para: pagamento
    campos:
      - { nome: termo_aceite, tipo: arquivo, obrigatorio: false }
  # Padrão da EJ: pagamento à vista (1 parcela). O self-loop abaixo existe só para casos excepcionais;
  # nenhuma outra parte do sistema depende de parcelamento.
  - acao: registrar_parcela
    de: pagamento
    para: pagamento            # self-loop: registra cada parcela
    campos:
      - { nome: valor_pago, tipo: money, obrigatorio: true }
      - { nome: comprovante, tipo: arquivo, obrigatorio: true }
  - acao: quitar
    de: pagamento
    para: concluido
    rotulo: "Pagamento quitado"
    guarda: "soma(registrar_parcela.valor_pago) >= projeto.valor_contratado"
```

### 6.2 Template `impressao_modelagem_3d` (v1)
Idêntico ao `website`, com as diferenças:
- `enviar_escopo.campos`: `escopo` (text, obr.), `estimativa_horas_modelagem` (number, opcional),
  `estimativa_filamento_g` (number, obr.), `material` (enum: PLA|PETG|ABS|TPU|resina, obr.),
  `arquivo_modelo` (arquivo .stl/.3mf/.step, opcional).
- `execucao` renomeada "Modelagem/Impressão", `sla_horas: 240`.
- `concluir_execucao.campos`: `fotos_peca` (arquivo, obr.), `filamento_real_g` (number, obr.).
- `entrega` aceita `forma_entrega` (enum: retirada|correio).

### 6.3 Como adicionar um serviço
1. Copiar um YAML de `fluxos/`, alterar `tipo_servico`, etapas, campos.
2. `node scripts/carregar_fluxos.js` (valida e cria versão).
3. Adicionar templates de prompt de IA em `prompts/<tipo_servico>/{orcamento,contrato}.md` (opcional;
   cai no genérico).
Projetos existentes continuam na versão de template com que nasceram.

## 8. REGRAS DE NEGÓCIO

### 8.1 Autorização (MUST, verificada no WF-02 e de novo no motor, dentro da transação)
Um membro M pode executar ação A no projeto P se TODAS:
1. M.ativo = true.
2. P.status = 'ativo' (exceto `retomar`, que exige 'pausado'; e `comentar`, permitido em qualquer status não-terminal).
3. A é transição válida a partir da etapa atual no template do projeto, ou é ação global.
4. Diretoria: M.diretoria == etapa_atual.diretoria_responsavel **OU** M.is_admin **OU**
   M.diretoria == 'presidencia'.
5. Se `env.EXIGIR_RESPONSAVEL_ATRIBUIDO=true` e a etapa tem responsável atribuído: M deve ser esse
   responsável, ou diretor/admin.
6. Regras específicas das globais:
   - `pausar`/`retomar`/`abandonar`: diretoria responsável da etapa atual, comercial, ou admin.
   - `reverter`: autor da ação revertida (até `JANELA_REVERSAO_HORAS`) OU admin.
   - `reatribuir`: admin ou membro da diretoria responsável.
   - Criar projeto: diretoria comercial ou admin.
Negação → resposta clara ao usuário dizendo QUEM pode agir (diretoria e responsável atribuído).

### 8.2 Validação de campos
Para cada campo do template: obrigatoriedade, tipo (text, number, money, date, enum, arquivo),
min/max, extensões permitidas para arquivo (`ARQUIVO_EXTENSOES_PERMITIDAS`), tamanho
(`ARQUIVO_TAMANHO_MAX_MB`). Campos ausentes → bot entra em modo diálogo pedindo um a um (§11.3).

### 8.3 Retrocesso (reverter)
- Nunca apaga. Cria ação `reverter` com `reverte_acao_id = X` e marca `X.revertida_por_id`.
- Alvo padrão: última ação não-revertida que mudou etapa ou status. `reverter <seq>` permitido só
  para a última (reverter em cadeia = chamar várias vezes, sempre do fim). Isso mantém consistência.
- Efeito: nova entrada em `etapas` igual à etapa de origem de X (nova `data_entrada`), status volta
  a `X.status_anterior`, campos projetados no projeto (valores, estimativas) recalculados por replay
  dos eventos não revertidos (função `projetar_estado`).
- Efeitos externos NÃO são desfeitos automaticamente (arquivos no Drive ficam; documentos ficam
  marcados como `reprovado` com motivo "revertido"). Notificar quem estava na etapa desfeita.
- Proibido reverter a partir de etapa terminal, exceto admin (reabrir projeto: limpa data_final).

### 8.4 Pausa e abandono
- `pausar`: status→pausado, etapa não muda, SLA congela (lembretes param). Motivo obrigatório.
- `retomar`: status→ativo, `prazo_sla` recalculado somando o tempo pausado.
- `abandonar`: motivo obrigatório, vai para etapa terminal `abandonado`, define `data_final`.
- Projeto em `aguardando_*` sem resposta por `DIAS_AUTO_ABANDONO` → sistema SUGERE abandono ao
  comercial (nunca abandona sozinho).

### 8.5 Rodízio de responsáveis
Etapas com `rodizio: true` recebem `responsavel_atribuido_id` ao entrar:
- Estratégia (DECIDIDA): **round robin sobre lista em ordem alfabética por `nome`** (collation pt-BR,
  sem acento/caixa) dos membros ativos+disponíveis da diretoria. Próximo = primeiro nome
  alfabeticamente MAIOR que o de `rodizio.ultimo_membro_id`; se não houver, volta ao início da lista.
  (Comparar por nome, não por posição, para que entradas/saídas de membros não bagunçem a ordem.)
- Membros com `disponivel=false` ou `ativo=false` são pulados. Se ninguém disponível → atribui nulo
  e notifica todos da diretoria + admins.
- Em reversão para uma etapa, reatribui à MESMA pessoa que tinha antes (continuidade), se disponível.
- `reatribuir` manual sobrescreve.
- Atualização de `rodizio` dentro da transação com `SELECT ... FOR UPDATE`.

### 8.6 SLA e lembretes (WF-10, a cada hora)
- Etapa aberta, projeto ativo, `now() > prazo_sla` → lembrete ao responsável (ou diretoria).
- Repetir a cada `LEMBRETE_INTERVALO_HORAS`. Após `ESCALONAR_APOS_LEMBRETES` lembretes → notifica
  diretor da diretoria/admins.
- Silenciar fora de `HORARIO_NOTIFICACAO_INICIO`–`FIM` e fins de semana (configurável).

### 8.7 Criação de projeto
Comercial envia: `nome_projeto`, `tipo` (lista de templates ativos), `cliente_nome`, `cliente_contato`
(email/telefone), `nome_lead`, `descricao` (opcional). Sistema: cria cliente (ou reaproveita por
email/doc), gera `codigo` `P-<ano>-<seq 4 dígitos>`, cria pasta no Drive, cria etapa inicial, ação
`criar_projeto` (seq 1), notifica.

## 14. IA PARA ORÇAMENTOS E CONTRATOS (WF-07)

Gatilho: efeitos `gerar_orcamento_ia` / `gerar_contrato_ia` (se `FEATURE_IA_DOCUMENTOS=true`; senão
notifica humano para criar manualmente e anexar).

Passos:
1. Montar contexto: dados do projeto, cliente, escopo, estimativas, histórico relevante, motivo da
   última reprovação (se houver), tabela de preços (tabela `precos`, sincronizada da planilha do
   Financeiro — §14.1).
2. **Cálculo de valores é determinístico em código** (Code node `calcular_orcamento`), NÃO pela IA.
   A IA só redige texto (descrição do escopo, cronograma, cláusulas específicas).
3. Chamar LLM com prompt de `prompts/<tipo>/<doc>.md` (ou `prompts/generico/`), saída JSON
   estruturada `{secoes: {descricao_escopo, entregaveis[], cronograma[], clausulas_especificas[]}}`.
4. Copiar template Google Docs (`_templates/orcamento_<tipo>`), substituir placeholders com valores
   calculados + texto da IA. Contrato usa template jurídico fixo revisado; IA só preenche anexos de
   escopo — cláusulas gerais NUNCA são geradas pela IA.
5. Inserir `documentos` (status rascunho, versão N+1). Disparar ação de sistema
   `orcamento_rascunho_pronto` / `contrato_rascunho_pronto` (membro_id = usuário-sistema "Therion Bot").
6. Notificar responsável da validação com link do Doc + botões Aprovar / Pedir correção.
7. Aprovado → exportar PDF, `status=aprovado`. **Envio ao cliente é MANUAL na v1** (DECIDIDO): o bot
   entrega o PDF ao responsável, que envia ao cliente e registra a ação (`cliente_aprovou` etc.).
   O envio automático virá no futuro; deixar o ponto de extensão pronto (ver §14.2).
8. Reprovado → motivo vira instrução adicional na regeneração. Após `IA_MAX_REGENERACOES` falhas,
   desliga IA para aquele documento e pede elaboração manual.
### 14.1 Tabela de preços (planilha do Financeiro + configuração pelo canal)
- Fonte de verdade: planilha Google da diretoria Financeira (`SHEETS_PRECOS_ID`, aba `SHEETS_PRECOS_ABA`),
  colunas: `chave | descricao | valor | unidade | tipo_servico | atualizado_por | atualizado_em`.
  Chaves esperadas (mínimo): `valor_hora_website`, `valor_hora_modelagem`, `filamento_pla_g`,
  `filamento_petg_g`, `filamento_abs_g`, `filamento_tpu_g`, `resina_ml`, `margem_percentual`,
  `impostos_percentual`, `parcelas_padrao` (padrão 1 = à vista), `arredondamento` (ex.: 10).
- Tabela espelho no banco:
  ```sql
  CREATE TABLE precos (
    chave text PRIMARY KEY, descricao text, valor numeric NOT NULL, unidade text,
    tipo_servico text, atualizado_por text, atualizado_em timestamptz NOT NULL DEFAULT now()
  );
  ALTER TABLE documentos ADD COLUMN precos_snapshot jsonb;
  ```
- Sync: WF-09b (mesmo cron do sync de membros + comando `/sync precos`). Linha inválida (valor não
  numérico, chave desconhecida) → ignorada e reportada ao diretor do Financeiro; valor anterior mantido.
- O orçamento gerado grava um **snapshot** dos preços usados em `documentos.precos_snapshot`, para que
  alterações futuras não mudem orçamentos já emitidos.
- Configuração pelo canal de interação (Telegram/e-mail):
  | Comando | Quem | Efeito |
  |---|---|---|
  | `/precos` | qualquer membro | Lista chaves, valores e última atualização. |
  | `/preco <chave> <valor>` | Financeiro (`cargo=diretor`) ou admin | Valida, pede confirmação, escreve na PLANILHA (fonte de verdade) e no banco; registra quem/quando; notifica o diretor do Financeiro. |
  | `/simular <tipo> horas=40` ou `filamento_g=200 material=PLA` | qualquer membro | Mostra o cálculo de `calcularOrcamento` sem criar nada. |
- Feature flag: `FEATURE_EDITAR_PRECOS_CANAL`.

### 14.2 Pontos de extensão para envio automático ao cliente (futuro)
- Efeito `enviar_documento_cliente` já declarado nos templates YAML após `aprovar_*_interno`, mas
  tratado como **no-op que apenas registra** enquanto a flag `ENVIO_AUTOMATICO_CLIENTE` for false.
- Criar `lib/envio_cliente.js` com interface `enviarDocumentoCliente({projeto, cliente, documento, canal})`
  retornando `{ok:false, motivo:'NAO_IMPLEMENTADO'}` na v1, e um subworkflow `WF-13 Envio ao Cliente`
  (Trigger → IF flag → Stop) para ser completado depois.
- Marcar todo ponto relacionado com o comentário padronizado
  `// TODO(ENVIO_AUTOMATICO_CLIENTE): <o que falta>` (encontrável com `grep -rn "TODO(ENVIO_AUTOMATICO_CLIENTE"`).
- Idem para assinatura eletrônica: `// TODO(ASSINATURA_ELETRONICA): ...` em `contrato_assinado`
  (hoje o PDF assinado é enviado manualmente como arquivo da ação).

### 14.3 Templates de documentos
Modelos oficiais de orçamento e contrato já existem no **Google Docs** da EJ. IDs via env

## 15. FLUXOGRAMA VISUAL (WF-08)

Entrada: `projeto_id`. Saída: PNG enviado ao solicitante e salvo como `fluxograma.png`.
Algoritmo (`gerar_mermaid`):
1. Carregar template (todas as etapas e transições) → nós e arestas base (cinza, tracejadas).
2. Carregar ações não revertidas em ordem → arestas percorridas (sólidas, rotuladas com
   `seq. tipo_acao (autor, dd/mm)`); ações revertidas em vermelho tracejado se `FLUXO_MOSTRAR_REVERTIDAS`.
3. Estilo dos nós: visitado (verde), atual (amarelo, negrito, com responsável e prazo), futuro (cinza),
   terminal (azul/vermelho).
4. Cabeçalho: código, nome, tipo, status, dias em andamento.
5. POST para renderer (`MERMAID_RENDER_URL`, ex. container `minlag/mermaid-cli` atrás de mini-API ou
   Kroki `POST /mermaid/png`) → PNG.
Opção `/fluxograma P-... simples` mostra só o caminho percorrido.

## 17. WORKFLOWS N8N (nó a nó)

Convenção: nomes `WF-NN Nome`. Subworkflows chamados com "Execute Workflow" passando JSON. Todo
workflow tem `errorWorkflow = WF-99`. Lógica não-trivial vive em `lib/*.js` (§18), carregada nos Code
nodes (copiada no deploy por `scripts/build_workflows.js`, que injeta o código de `lib/` nos nós
marcados com `// @include lib/<arquivo>.js`).

### WF-01a Entrada Telegram
1. **Webhook** `POST /telegram` (responder imediatamente 200; "Respond: Immediately").
2. **IF** header `x-telegram-bot-api-secret-token` == `$env.TELEGRAM_WEBHOOK_SECRET` → senão Stop.
3. **IF** `CANAL_TELEGRAM_ATIVO`.
4. **Code: normalizar_telegram** (`lib/normalizadores.js#telegram`) → Comando Normalizado
   (message, callback_query, document, photo; `idempotency_key = telegram:update:<update_id>`).
5. **Execute Workflow** → WF-03 Roteador.
6. **Execute Workflow** → WF-05 Responder (com `canal=telegram`, `chat_id`, resposta).
   (Para callback_query: também `answerCallbackQuery`.)

### WF-01b Entrada WhatsApp
1. **Webhook** `GET /whatsapp` → **Respond** `hub.challenge` se `hub.verify_token` confere.
2. **Webhook** `POST /whatsapp` → **Code: verificar_assinatura_meta** (HMAC SHA256 do raw body com
   `WHATSAPP_APP_SECRET`) → **Respond 200**.
3. **Code: normalizar_whatsapp** (texto, interactive button_reply/list_reply, document, image;
   ignorar `statuses`). `idempotency_key = whatsapp:<message.id>`.
4. → WF-03 → WF-05.

### WF-01c Entrada E-mail
1. **Email Trigger (IMAP)** caixa `INBOX`, marcar como lido, baixar anexos.
2. **Code: normalizar_email**: extrai `[P-AAAA-NNNN]` do assunto, primeira linha não vazia do corpo
   como comando, linhas `campo: valor` como campos, ignora citação (`>`/assinatura).
   `idempotency_key = email:<Message-ID>`. Verifica `Authentication-Results` (dkim=pass).
3. → WF-03 → WF-05 (resposta como reply no mesmo thread: `In-Reply-To`).

### WF-01d Entrada Forms
1. **Webhook** `POST /forms` → **Code: verificar_hmac** → **Respond 200**.
2. **Code: normalizar_forms**: mapeia `form_id` → comando (`novo` ou `acao` + tipo) usando
   `config/forms.yaml`; respostas → campos; uploads (IDs do Drive) → arquivos já no Drive.
   `idempotency_key = forms:<responseId>`.
3. → WF-03 → WF-05 (resposta por e-mail/canal preferido, pois o Forms não tem canal de volta).

Apps Script (no Form):
```javascript
function onFormSubmit(e) {
  const payload = JSON.stringify({
    form_id: e.source.getId(),
    response_id: e.response.getId(),
    email: e.response.getRespondentEmail(),
    respostas: e.response.getItemResponses().map(r => ({ titulo: r.getItem().getTitle(), valor: r.getResponse() })),
    enviado_em: e.response.getTimestamp().toISOString()
  });
  const secret = PropertiesService.getScriptProperties().getProperty('FORMS_HMAC_SECRET');
  const sig = Utilities.computeHmacSha256Signature(payload, secret)
    .map(b => ('0' + (b & 0xff).toString(16)).slice(-2)).join('');
  UrlFetchApp.fetch(PropertiesService.getScriptProperties().getProperty('WEBHOOK_URL'), {
    method: 'post', contentType: 'application/json', payload,
    headers: { 'X-Signature': 'sha256=' + sig }, muteHttpExceptions: true
  });
}
```

### WF-02 Identificação (subworkflow; chamado pelo WF-03)
1. **Postgres**: `SELECT * FROM membros WHERE <coluna do canal> = $1 AND ativo`.
2. **IF** encontrado → retorna `{membro}`.
3. Senão **IF** comando é `vincular`/`codigo` → permite seguir sem membro.
4. Senão → `{erro: NAO_IDENTIFICADO}`.
5. **Code: rate_limit** (contagem por id_externo na última janela, tabela ou Redis opcional).

### WF-03 Roteador de Comandos
1. **Execute Workflow Trigger** (recebe Comando Normalizado).
2. **Postgres: checar idempotência** `SELECT resposta FROM acoes WHERE idempotency_key=$1` (e/ou
   tabela `requisicoes_processadas`) → se existir, retorna resposta anterior (Stop).
3. → WF-02 Identificação.
4. **Code: carregar_sessao** (se há diálogo aberto, mescla entrada com estado).
5. **Code: parse_comando** (`lib/comandos.js`) → `{comando, args}`.
6. **Switch** por `comando`:
   - `ajuda` → Code template de texto.
   - `meus` / `projetos` / `projeto` / `historico` → Postgres queries (`sql/consultas.sql`) → Code
     formatar.
   - `novo` → WF-04 (operação `criar_projeto`).
   - `acao` / `pausar` / `retomar` / `abandonar` / `reverter` / `reatribuir` / `comentar` → WF-04.
   - `fluxograma` → WF-08.
   - `canal` / `ausente` / `disponivel` → Postgres UPDATE + escrita na planilha.
   - `vincular` / `codigo` → Code + Postgres + SMTP.
   - `cancelar` → apagar sessão.
   - desconhecido → se `FEATURE_NLU` → **Code/HTTP: nlu_extrair** → confirmação; senão ajuda.
7. **Code: salvar_sessao** se resposta for `CAMPOS_FALTANTES` ou confirmação pendente.
8. Retorna Resposta.

### WF-04 Motor de Fluxo (núcleo — tudo dentro de UMA transação)
Entrada: `{operacao, membro, projeto_codigo?, tipo_acao, campos, arquivos, observacoes, canal, idempotency_key, confirmado}`.
1. **Code: Config**.
2. **Postgres (transação)**: `BEGIN; SELECT * FROM projetos WHERE codigo=$1 FOR UPDATE;`
   (n8n Postgres node não mantém transação entre nós → implementar passos 2–9 como **uma única
   função PL/pgSQL** `registrar_acao(jsonb) RETURNS jsonb` OU um único Code node usando `pg` client
   com transação. **Decisão: PL/pgSQL para gravação + Code node para validação prévia.**)
   Pré-validação no Code node (`lib/motor.js#validar`): carrega projeto, template, etapa atual,
   valida autorização (§8.1), transição, campos (§8.2), guardas. Se faltar campo → retorna
   `CAMPOS_FALTANTES` (sem gravar). Se não `confirmado` e ação for destrutiva (reverter, abandonar) →
   retorna pedido de confirmação.
3. **Execute Workflow WF-06 (upload de arquivos)** — antes da gravação, para ter `drive_file_id`.
   (Se a gravação falhar depois, arquivos ficam em `_pendentes/` e um job limpa após 24h.)
4. **Code: escolher_responsavel** (`lib/rodizio.js`) — calcula candidato (será confirmado no SQL).
5. **Postgres: `SELECT registrar_acao($json)`** — função faz, atomicamente:
   a. `SELECT ... FOR UPDATE` no projeto; compara `versao` esperada (otimista) → CONFLITO se mudou.
   b. Revalida transição e permissão (defesa em profundidade).
   c. `seq = max(seq)+1`; INSERT em `acoes`.
   d. Se muda de etapa: UPDATE `etapas.data_saida` da atual; INSERT nova etapa com
      responsável/prazo; UPDATE `rodizio`.
   e. UPDATE `projetos` (etapa_atual_id, status, campos projetados, data_final, versao+1).
   f. Para `reverter`: UPDATE `acoes.revertida_por_id` do alvo.
   g. Retorna `{acao, projeto, etapa_nova, efeitos[], destinatarios[]}`.
6. **Split efeitos** → **Switch** por efeito → Execute Workflow (WF-06/WF-07) de forma
   **assíncrona** (n8n: "Wait for sub-workflow: false") para não travar a resposta.
7. **Execute Workflow WF-11 regenerar_log** (assíncrono) se `FEATURE_EXPORT_LOG_DRIVE`.
8. **Execute Workflow WF-05 Notificar** destinatários: responsável atribuído da nova etapa (ou toda
   a diretoria se nulo), membro original do projeto (resumo), quem foi afetado por reversão.
9. Retorna Resposta `ACAO_REGISTRADA`.

### WF-05 Notificações / Respostas
1. **Execute Workflow Trigger** `{destinatarios[] | resposta_direta, mensagem, botoes, anexos}`.
2. **Code: resolver_canal** por membro (preferido → habilitado + flag ativa → fallback).
3. **Code: horario_silencioso** (notificações não urgentes adiadas: INSERT em `notificacoes` com
   status pendente; respostas diretas sempre enviadas).
4. **Postgres INSERT `notificacoes`** (outbox).
5. **Switch canal** → **Telegram** (sendMessage com `reply_markup.inline_keyboard`; sendPhoto para
   PNG) | **HTTP WhatsApp** (`/messages`, tipo `interactive` até 3 botões, `template` fora da janela de
   24h) | **Send Email** (HTML simples; botões viram instruções "responda com: aprovar").
6. **Postgres UPDATE** status enviada/falhou; falha → retry com backoff (WF-10 reprocessa pendentes
   com `tentativas < 5`), depois fallback para e-mail.
Renderização por canal em `lib/render.js` (Telegram MarkdownV2 com escape; WhatsApp texto + botões;
e-mail HTML).

### WF-06 Drive/Docs
Operações via Switch: `criar_pasta_projeto`, `baixar_e_subir` (Telegram getFile / WhatsApp media URL /
anexo IMAP → Google Drive Upload), `mover`, `lixeira`, `copiar_template`, `substituir_placeholders`
(Google Docs node "Update: replaceAllText"), `exportar_pdf` (Drive export `application/pdf`).
Validar extensão/tamanho antes do upload. Retorna `{drive_file_id, url}`.

### WF-07 IA Documentos
Conforme §14: Postgres (contexto) → Code `calcular_orcamento` → Code montar prompt → **HTTP Request**
(ou nó Anthropic) com timeout/retry 2x → Code validar JSON (schema) → WF-06 copiar template +
placeholders → Postgres INSERT documentos → WF-04 ação de sistema `*_rascunho_pronto` → WF-05 notificar
validador com link e botões.

### WF-08 Fluxograma
Trigger → Postgres (projeto, template, ações, etapas) → Code `gerar_mermaid` → HTTP POST renderer
(responseFormat: file) → WF-06 upload/atualiza `fluxograma.png` → retorna binário para WF-05.

### WF-09 Sync Membros (cron `SYNC_MEMBROS_CRON` + comando admin `/sync`)
Google Sheets Read → Code `validar_linhas` (email válido, diretoria no enum, telefone → E.164; linhas
inválidas listadas) → Postgres UPSERT por email → Code diff (novos/desativados/indisponíveis) →
novos: e-mail de boas-vindas; desativados/indisponíveis: reatribuir etapas abertas (WF-04
`reatribuir` como sistema) → relatório de erros para admins.

### WF-10 SLA, lembretes e reenvio (cron horário)
Postgres: etapas vencidas (projeto ativo) → Code agrupar por responsável → WF-05 (lembrete ou
escalonamento) → reprocessar `notificacoes` pendentes/falhas → sugerir abandono (§8.4) → limpar
`sessoes_chat`/`vinculos_pendentes` expirados e arquivos `_pendentes/` > 24h.

### WF-11 Backup / Export
- `regenerar_log(projeto_id)`: Postgres ações → Code JSONL → Drive (substitui `log.jsonl`).
- Cron diário 03:00: `pg_dump` (Execute Command, ou container de backup separado) → `_exports/` com
  retenção de 30 diários + 12 mensais. Exportar workflows n8n (CLI `n8n export:workflow --all`) para
  o repositório git.

### WF-12 Relatórios / Dashboard
Cron semanal (segunda 09:00) e comando `/relatorio` (admin/presidência): projetos por etapa, tempo
médio por etapa, taxa de conversão orçamento→contrato, projetos parados > SLA, receita contratada no
período. Envio por e-mail/Telegram + (MAY) aba "Dashboard" numa planilha Google atualizada ou
Metabase/Grafana lendo o Postgres (views em `sql/views.sql`).

### WF-99 Error Handler
Error Trigger → Code formatar (workflow, nó, mensagem, execution id, sem dados pessoais) → Telegram
para grupo de admins/tech → se a execução tinha remetente, responde "Erro interno, a equipe foi
avisada (ref: <execution_id>)".

- Motor: cada transição dos templates com campos válidos/faltantes; guarda de `quitar`.
- Reversão: avançar 3 vezes, reverter 2, `projetarEstado` == estado esperado; reverter de terminal negado.
- Rodízio: round-robin pula indisponíveis; ninguém disponível → nulo.
- Parser: comandos com/sem barra, aspas, acentos, código no meio do texto.
- Normalizadores: fixtures reais de payload de cada canal em `tests/fixtures/`.
- Idempotência: mesmo `idempotency_key` duas vezes → uma ação só.
- Concorrência: duas ações simultâneas no mesmo projeto → uma CONFLITO.

---------------------------------------------------------------------------------------------------
## 19. ERROS, IDEMPOTÊNCIA, CONCORRÊNCIA

- **Idempotência**: toda entrada tem `idempotency_key` derivada do ID nativo do provedor (webhooks
  são reentregues). Tabela `requisicoes_processadas(idempotency_key PK, resposta jsonb, criado_em)`
  gravada ao fim do WF-03; checada no início. `acoes.idempotency_key UNIQUE` é a última barreira.
- **Concorrência**: `SELECT ... FOR UPDATE` + `projetos.versao`. Conflito → mensagem "O projeto foi
  alterado por outra pessoa agora, verifique com /projeto P-..." .
- **Efeitos externos** (Drive, IA, notificação) acontecem DEPOIS do commit e são re-tentáveis; falha
  em efeito NÃO desfaz a ação; é registrada e alertada (WF-99) e pode ser reexecutada por admin
  (`/reprocessar <acao_id>`).
- **Timeouts**: webhooks respondem 200 imediatamente; processamento segue assíncrono.
- **Falha do Drive** no upload pré-gravação → ação não é registrada, usuário é avisado para reenviar.
- **LLM fora do ar** → notificar responsável para fazer manualmente; projeto não trava.
- Logs: sem dados pessoais em mensagens de erro; usar IDs.

## 20. SEGURANÇA, REDE E LGPD

Rede:
- Host com n8n+Postgres+renderer em Docker Compose, portas ligadas só em `127.0.0.1`/interface Tailscale.
- **Cloudflare Tunnel** (`cloudflared`) com ingress apenas para `https://<dominio>/webhook/*` →
  `http://n8n:5678`; demais paths → 404. WAF/rate limiting do Cloudflare ativado.
- Editor do n8n acessível somente via Tailscale (`http://<host-tailscale>:5678`), com usuário/senha e
  2FA se disponível. `N8N_ENCRYPTION_KEY` definido e guardado fora do servidor.
- Postgres sem porta pública.
Aplicação:
- Validação de assinatura em todos os webhooks (§17). Rate limit por remetente.
- Princípio do menor privilégio na Service Account (só o Shared Drive e a planilha).
- Segredos via Docker secrets / Credentials do n8n.
LGPD:
- Dados de clientes (nome, contato, CPF/CNPJ) e membros: base legal = execução de contrato / legítimo
  interesse; registrar no termo da EJ.
- Minimização: bots exibem CPF/CNPJ mascarado; IA não recebe documento/endereço/telefone.
- Retenção: projetos abandonados há > `RETENCAO_ABANDONADOS_MESES` (padrão 24) têm dados pessoais do
  cliente anonimizados (job mensal).
- Mensagens trafegam por terceiros (Meta, Telegram, Google): documentar no aviso de privacidade.
- Direito de exclusão: comando admin `/anonimizar_cliente <id>`.
